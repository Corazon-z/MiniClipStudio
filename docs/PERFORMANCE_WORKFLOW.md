2026-11-13。目标是可复现、数据驱动的工程判断，不承诺所有机器/视频都达到同样速度。功能正确优先；测量从现在开始，局部优化在对应功能验收后逐项对照，S17保留为完整版本的集中优化。

## 指标与陷阱

- 墙钟是用户等了多久；进程CPU时间是各线程CPU消耗之和。不能把CPU时间/逻辑核数直接说成某个阶段性能，更不能把阶段墙钟当CPU采样。
- API计时到发布点；进程墙钟另含启动/析构清理/退出与捕获日志。峰值工作集覆盖进程生命，不是精确任务增量；工作集不是private bytes或显存。
- 阶段计时是部分API边界，过滤器可能延迟计算，内部库可能多线程；不能简单求和还原总时间。需要采样分析才能解释函数热点。
- 三次运行报告中位数和范围，不用三条数据宣传可靠P95/P99；更完整负载测试需更多样本与稳定环境。
- 输入、尺寸、fps、裁剪、编码器、CRF/preset、线程、构建和硬件必须记录。Debug/Release差异不能当算法优化；改质量参数也不能只报速度。

## 下一项优化实验怎样做

1. 先固定一组通过正确性测试的输入，补真实H264短/长视频与不同分辨率、帧率，原素材不上传。
2. Release、同参数、不打断点测基线；预热后多次运行，记录机器负载与原始数据。
3. 用VS Performance Profiler CPU Usage看调用树/热点；当前API计时只是粗定位。官方说明见[CPU分析工具](https://learn.microsoft.com/en-us/visualstudio/profiling/cpu-usage)。本轮没有实际运行该GUI分析器。
4. 一次做一个可解释变化，如独立调整编码线程、复用已定位分配热点，或对长输入短片段评估seek+早停；后者要重新验证关键帧前置解码、公共时间起点、尾部与错误契约。
5. 相同数据重跑正确性、质量与性能对照。记录变快/变慢和资源代价，不只保存最好一次；无收益就撤回或保留为负结果说明。

## 后续岗位训练线（尚未实现）

S03验收后先做CPU热点与一个小实验；再规划Linux headless CLI验证/平台I/O与测量适配。CMake/Linux迁移是独立变更，确认方案后再做，不因本计划自动安装或搬项目。

之后用有界任务队列研究并发：限制同时任务数、内存、取消与背压，测吞吐及单任务延迟，避免N个任务各开N线程导致超额竞争。不要把目前同步CLI说成已建云端弹性服务。

GPU阶段先查询真实能力和驱动，对比CPU编码与硬件编码的端到端时间、传输、资源及质量；不是把CRF23和另一编码器的数字23当同质量。模型推理阶段再评估一个具体模型的CPU/GPU、数据传输、预热和精度变化。ONNX Runtime有[性能分析工具](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html)可作后续参考；本轮没有接入推理框架、量化或算子融合。

## S04播放的观测与后续实验（2026-11-13）

播放的目标是按声卡速度稳定交付，不能以“解码越快播放越快”为优化目标。当前记录队列峰值、实际设备容量、已交付/消费估算帧数和饥饿区间；有界8×1024帧队列产生背压，事件驱动/有限等待避免空转。同步、取消唤醒与所有权属于当前正确性。

真实设备静音测试观察到2秒=96000帧全部消费、队列峰值8，实际设备容量4800帧，测试期间饥饿区间0；仅代表本机短素材，不能宣传无卡顿或低延迟成品。停止测量、最终报告路径见worklogs/2026-11-13-s04-audio-playback.md。没有新的CPU Usage采样/GPU测量。

人工听感/长素材验收后，固定采样率/源格式/输出设备/设备容量/负载，以Release记录CPU、private bytes/工作集、句柄、停止响应及饥饿分布；再做单变量队列/缓冲实验，比较延迟与稳定性。不要先改无锁队列或提高线程数；软件增益对已提交缓冲有延迟，设备消费估算不是完整硬件时钟。

## S06录制的性能意识（2026-11-14）

单worker读包/编码便于维护，GUI取单图不阻塞采集，但编码慢可能让16MiB设备缓冲满。先测实际交付间隔、编码CPU/墙钟、内存、源/成片帧数和停止延迟，再对照preset/线程/硬件编码；本轮没有新的热点采样或提速比例。邮箱替换不等于录制丢帧，CFR成片帧数不等于摄像头实际交付帧数。

Debug/Release已做本机短录和重解，尾部差50—100ms不代表物理同步/长期稳定。先补GUI/长录与音画信号测量，见[摄像头说明](CAMERA_CAPTURE.md)。
